# セキュリティ更新の準備と軽微な更新の自動反映

## 承認された作業範囲

2026-10-22 のユーザー依頼により、定期監視で修正版を検知したら、元の作業場所とは別の worktree に更新案を用意する。対象は Sora Gallery と Sora Player。同日、ユーザーは以下の条件をすべて満たす Gallery のパッチ更新について、main への反映・push・本番デプロイまで明示的に許可した。これ以外の反映と、停止後の再公開はユーザーの判断を待つ。Player は引き続き更新案の準備までとする。

重大な危険がある場合は [緊急停止方針](emergency-shutdown.md) を先に適用する。修正版の調査・検証が終わるまで、必要な停止を遅らせない。

## 自動で準備する更新

- 公式の修正情報があり、対象の脆弱性を修正できる同一メジャー内のパッチ・マイナー更新。
- 依存関係の修正版に合わせた必要最小限の互換修正と、関連するドキュメントの同期。
- Node.js の修正版は、更新案の worktree の `mise.toml` だけで指定する。Homebrew、グローバル設定、元の作業場所を切り替えない。

メジャー更新、大きなAPI変更、データ移行、広範囲の実装修正、新しい権限や契約が必要な場合は、調査結果と必要な判断を報告して止める。`npm audit fix --force`、脆弱性の無視、根拠のない override やダウングレードで件数だけを消さない。

## 準備の進め方

1. 公開中・利用中の構成と、修正版の公式情報を照合する。影響を受けないコンポーネントの更新まで広げない。
2. 対象リポジトリの適切なコミットから専用 worktree と `codex/security-…` ブランチを作る。既存の準備済み更新案を先に確認し、同じ問題・修正版に複数の案を作らない。元の作業場所、未コミット変更、ユーザーのブランチや worktree を変更・削除しない。
3. 修正対象の依存関係とロックファイルを更新する。必要な依存関係や指定Node.jsは公式の配布元から導入してよいが、無関係なツールやブラウザ拡張を追加しない。依存パッケージのインストール時スクリプトは原則無効にし、必要性と内容を確認できないものを実行しない。
4. `npm ci` 等で作り直した環境に対して監査、既存テスト、静的チェック、型チェック、本番ビルドを行う。変更に応じた意味のある回帰確認を行う。
5. Gallery は、非Git管理の `public/videos.json` と本番反映に必要なローカル設定を区別して扱う。現在の本番データ、または停止前の確認記録との一致が確認できる公開データだけを使用し、未公開の変更を混ぜない。必要なファイルだけ worktree にコピーし、認証ファイルや非公開の Player データを一括コピーしない。これらを Git に追加しない。
6. Gallery のデータ検証、公開素材の配信検査、共有ページの生成も確認する。必要な D1 設定とデプロイ先が元の本番と一致することを、秘密情報を記録せず確認する。
7. 差分を確認し、更新案の worktree 内で日本語のローカルコミットを作ってよい。以下の自動反映条件をすべて満たす Gallery 更新のみ、main への反映・push・本番デプロイへ進める。それ以外は元の main を変更せず、push・PR作成・デプロイ・再公開を行わない。

依存関係の導入や検証に失敗した場合、承認が必要な操作を迂回しない。成功していない検証を成功扱いにせず、準備途中として報告する。

## Gallery の自動反映条件

以下をすべて満たす場合だけ、ユーザーの返答を待たず反映してよい。「軽微」は警告の重大度ではなく、更新による変更範囲で判定する。

- 公式に脆弱性の修正が確認できる安定版への更新である。直接・間接の依存関係を含め、変更する各パッケージのメジャー・マイナー番号が同じで、パッチ番号だけが増える。例は `1.2.3 → 1.2.4`。マイナー更新、メジャー更新、プレリリース、追加・削除・配布元変更を含む場合は自動反映しない。
- 差分は `package.json` の依存関係の版指定と `package-lock.json` の対応する変更だけ。npm scripts、UI、API、DB、Node.js 指定、ビルド・デプロイ設定、公開データの変更を含まない。依存関係側の変更履歴も読み、移行や機能・挙動変更の懸念があれば判断を待つ。
- 上記の全検証と「コマンドでの反映準備済み」の条件を満たす。修正対象が解消し、監査で新しい脆弱性がなく、既知問題の悪化もない。ブラウザ確認は自動反映の必須条件にはしないが、未確認なら報告に明記する。
- 本番は正常に公開中で、停止用ヘッダーがなく、公開停止・障害・状態不明ではない。実行直前にも確認する。停止中なら修正済みでも自動再公開しない。
- 元の作業場所は main で変更がなく、fetch 後の `origin/main` と一致する。未pushコミット、未コミット変更、競合、別ブランチ、他の作業・デプロイとの同時進行があれば準備までに留める。ユーザーの変更を stash・reset して条件を満たそうとしない。
- 公開中のコミットと基準コミットを照合し、未公開のアプリ変更を巻き込まない。運用文書など配信内容に影響しない差分だけを根拠付きで区別できる場合を除き、一致しなければ自動反映しない。公開動画一覧は件数だけでなく内容が現本番と一致し、本番設定・D1・既存アカウント・プロジェクトも一致する。

反映直前に remote、本番のデプロイ、データ、検証対象コミットと成果物が変わっていないことを再確認する。main は `git merge --ff-only` で更新コミットへ進め、`git push origin main` を行う。push に成功し、remote main が検証済み更新コミットであることを確認してから、専用 worktree の検証済み `dist/` を以下のコマンドでデプロイする。強制push、ブランチ保護の回避、他の変更を含むマージ、PR作成は行わない。途中で変更が入った場合は中断し、更新した基準から検証をやり直す。

```bash
mise exec -- npx --no-install wrangler pages deploy dist --project-name sora-gallery --branch main
```

反映後は、本番のトップページ、参照される JS/CSS、動画一覧、既存の個別動画ページ、GET likes API を読み取りで確認する。HTTP成功だけでなく、成果物・動画一覧・共有メタ情報・API応答の内容を照合する。いいねの試験書き込みや攻撃リクエストは行わない。デプロイID、ソースコミット、変更した版、検証結果、本番確認結果をチャットへ報告する。軽微な更新が正常完了した通知ではカレンダーの予定を追加しない。

push・デプロイ・公開後確認のいずれかが失敗したら、その段階を明記して緊急通知し、後続の自動反映を保留する。main の更新と本番反映を混同しない。根拠なく旧版へ戻したり、成功と報告したりしない。重大な危険が確認された場合は緊急停止方針を適用する。認証・権限不足は迂回せず、ユーザーの対応を待つ。

## 「コマンドでの反映準備済み」の完成条件

- 修正する脆弱性・変更前後の版が特定され、監査で対象問題の解消を確認できる。無関係な既知の警告は別に明記する。
- テスト・静的確認・ビルドが成功し、必要な公開用データとローカル設定が揃っている。
- Gallery の検証済み `dist/` が更新案の worktree にあり、通常のギャラリーである。停止用 `maintenance/` と取り違えない。
- worktree の場所、元コミットと更新コミット、変更した版、確認結果、残る警告、未確認事項、実行すべきコマンドをチャットに示す。公開用データの内容確認も含める。
- コミット、依存関係、ビルド成果物、公開用データ、設定のいずれかが後から変わった場合は、再検証が必要とする。

Gallery の本番反映コマンドは、準備した worktree で実行する形で示す。

```bash
mise exec -- npx --no-install wrangler pages deploy dist --project-name sora-gallery --branch main
```

Player は公開用サイトではないため、更新案の取り込み・起動確認の手順を示し、Gallery のデプロイとは区別する。

ブラウザの再生・音声・操作を確認していなければ「ブラウザ動作は未確認」と明記する。コマンド検証だけで全面的に本番反映可能と断定しない。未完了の条件があれば「準備途中」とし、デプロイするだけの状態とは呼ばない。

## 通知と未確認事項

軽微な更新が全検証と公開後確認を含め正常完了し、別の要対応事項がなければチャットだけに報告し、Googleカレンダーの予定を追加しない。重大な問題、公開停止、更新準備・push・デプロイ・公開後確認の失敗、ユーザーの判断や対応が必要な場合は、引き続きチャットとGoogleカレンダーに通知する。未解消の危険や失敗を軽微な完了報告にまとめて通知対象から外さない。同じ更新案の進捗を毎日重複通知せず、メールは使わない。

これは毎朝7時のローカル定期監視の実行時に進める。Mac・アプリの起動と必要なネットワーク・認証が必要である。新たな修正版の検知から更新準備・自動本番反映までの無人の通し試験は未実施であり、設定を試すために不要な版変更や本番デプロイを行わない。
