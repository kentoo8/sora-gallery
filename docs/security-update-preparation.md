# セキュリティ更新を反映直前まで準備する

## 承認された作業範囲

2026-10-22 のユーザー依頼により、定期監視で修正版を検知したら、元の作業場所とは別の worktree に更新案を用意する。対象は Sora Gallery と Sora Player。通常デプロイと停止後の再公開は、ユーザーの判断を待つ。

重大な危険がある場合は [緊急停止方針](emergency-shutdown.md) を先に適用する。修正版の調査・検証が終わるまで、必要な停止を遅らせない。

## 自動で準備する更新

- 公式の修正情報があり、対象の脆弱性を修正できる同一メジャー内のパッチ・マイナー更新。
- 依存関係の修正版に合わせた必要最小限の互換修正と、関連するドキュメントの同期。
- Node.js の修正版は、更新案の worktree の `mise.toml` だけで指定する。Homebrew、グローバル設定、元の作業場所を切り替えない。

メジャー更新、大きなAPI変更、データ移行、広範囲の実装修正、新しい権限や契約が必要な場合は、調査結果と必要な判断を報告して止める。`npm audit fix --force`、脆弱性の無視、根拠のない override やダウングレードで件数だけを消さない。

## 準備の進め方

1. 公開中・利用中の構成と、修正版の公式情報を照合する。影響を受けないコンポーネントの更新まで広げない。
2. 対象リポジトリの適切なコミットから専用 worktree と `codex/security-…` ブランチを作る。既存の準備済み更新案を先に確認し、同じ問題・修正版に複数の案を作らない。元の作業場所、未コミット変更、ユーザーのブランチや worktree を変更・削除しない。
3. 修正対象の依存関係とロックファイルを更新する。必要な依存関係や指定Node.jsは公式の配布元から導入してよいが、無関係なツールやブラウザ拡張を追加しない。依存パッケージのインストール時スクリプトは原則無効にし、必要性と内容を確認できないものを実行しない。
4. `npm ci` 等で作り直した環境に対して監査、既存テスト、静的チェック、型チェック、本番ビルドを行う。変更に応じた意味のある回帰確認を行う。
5. Gallery は、非Git管理の `public/videos.json` と本番反映に必要なローカル設定を区別して扱う。現在の本番データ、または停止前の確認記録との一致が確認できる公開データだけを使用し、未公開の変更を混ぜない。必要なファイルだけ worktree にコピーし、認証ファイルや非公開の Player データを一括コピーしない。これらを Git に追加しない。
6. Gallery のデータ検証、公開素材の配信検査、共有ページの生成も確認する。必要な D1 設定とデプロイ先が元の本番と一致することを、秘密情報を記録せず確認する。
7. 差分を確認し、更新案の worktree 内だけで日本語のローカルコミットを作ってよい。元の main へのマージ、push、PR作成、通常デプロイ、再公開は行わない。

依存関係の導入や検証に失敗した場合、承認が必要な操作を迂回しない。成功していない検証を成功扱いにせず、準備途中として報告する。

## 「コマンドでの反映準備済み」の完成条件

- 修正する脆弱性・変更前後の版が特定され、監査で対象問題の解消を確認できる。無関係な既知の警告は別に明記する。
- テスト・静的確認・ビルドが成功し、必要な公開用データとローカル設定が揃っている。
- Gallery の検証済み `dist/` が更新案の worktree にあり、通常のギャラリーである。停止用 `maintenance/` と取り違えない。
- worktree の場所、元コミットと更新コミット、変更した版、確認結果、残る警告、未確認事項、実行すべきコマンドをチャットに示す。公開用データの内容確認も含める。
- コミット、依存関係、ビルド成果物、公開用データ、設定のいずれかが後から変わった場合は、再検証が必要とする。

Gallery の本番反映コマンドは、準備した worktree で実行する形で示す。

```bash
mise exec -- npx --no-install wrangler pages deploy dist --project-name sora-gallery --branch main
```

Player は公開用サイトではないため、更新案の取り込み・起動確認の手順を示し、Gallery のデプロイとは区別する。

ブラウザの再生・音声・操作を確認していなければ「ブラウザ動作は未確認」と明記する。コマンド検証だけで全面的に本番反映可能と断定しない。未完了の条件があれば「準備途中」とし、デプロイするだけの状態とは呼ばない。

## 通知と未確認事項

新しい更新案の準備完了・準備失敗・判断が必要になった場合に、既存のチャットとGoogleカレンダーの通知へまとめる。同じ更新案の進捗を毎日重複通知せず、メールは使わない。

これは毎朝7時のローカル定期監視の実行時に進める。Mac・アプリの起動と必要なネットワーク・認証が必要である。新たな修正版の検知から worktree 準備までの無人の通し試験は未実施であり、更新案を作るために不要な版変更を行わない。
